# 异步 / 多线程改造方案

> 目标：让项目里有一条**能从入口追到出口的异步调用链路**，而不是零散地撒几个 `@Async`。
> 判断标准：接口耗时下降 + 一个 `traceId` 串起多个线程 + 外部依赖挂掉时接口仍可用。

---

## 0. 现状诊断（为什么现在是"零异步"）

全仓搜索 `@Async` / `ExecutorService` / `ThreadPool` / `CompletableFuture` / `@Transactional` / `ThreadLocal`：**0 命中**。

所有请求都跑在 Tomcat 的 `http-nio-8080-exec-*` 工作线程上，串行阻塞：

| 位置 | 现状 | 问题 |
|---|---|---|
| `AiChatService.ask()` | `detectIntent`（1 次 LLM）→ 再 `handleShop`/`handleChat`（第 2 次 LLM） | 一次问答 4~7 秒，**全程占着 Tomcat 线程**；并发 50 就打满 200 线程 |
| `AdminController.stats()` | 4 次查询串行；`revenue` 把**所有**已完成订单捞进内存 `reduce` | 数据量一大就 OOM；4 次 IO 白白串行等待 |
| `OrdersController.create()` | 校验 + 落库 + 明细，**没有事务** | 并发/异常时可能只写了一半；将来加"通知摊主/统计"会继续拖慢主链路 |
| 全项目 | 没有 traceId | 异步后日志会散在不同线程，出问题无法定位 |

所以第一步不是加 `@Async`，而是**先修事务、再建线程池、最后拆链路**。

## 1. 目标链路（答辩/面试就讲这张图）

```
HTTP 请求
  └─ TraceIdFilter           生成 traceId → MDC      [Tomcat 线程]
      └─ Controller
          ├─ 并行扇出 ──┬─ aiExecutor: 意图识别 (LLM, 预算 1.2s)
          │             └─ aiExecutor: 知识检索 (向量库, 预算 1.5s)
          ├─ 聚合 + 时间预算 8s，超时走降级话术
          ├─ 主事务写库（订单 + 明细）
          └─ 事务提交后 ─▶ bizExecutor: 推送摊主 / 写日志 / 刷看板   [异步线程]
                              └─ 失败 → outbox 表 → 定时任务重试
```

一条链路里同时用到了：**Future 组合、线程池隔离、超时、降级、事务边界、事件驱动、重试补偿、上下文传递、指标观测**。这就是"异步调用链路"和"加了个 @Async"的区别。

## 2. 四个落地场景（按性价比排序）

### 场景 A：AI 问答并行扇出 + 时间预算 + 降级 ★必做

**现状**：`AiChatService.ask()` 串行两次 LLM 调用，4~7 秒。

**改法**：意图识别和知识检索**同时发起**（不用等意图结果再去检索），各自带超时，整体带时间预算。

```java
public ChatAnswer ask(String question, List<Map<String, String>> history) {
    // 1) 两个互相独立的远程调用，并行发起
    CompletableFuture<String> intentFuture = CompletableFuture
            .supplyAsync(() -> detectIntent(question), aiExecutor)
            .orTimeout(1200, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> { log.warn("意图识别降级 traceId={}", MDC.get("traceId")); return "chat"; });

    CompletableFuture<List<Document>> docsFuture = CompletableFuture
            .supplyAsync(() -> safeSearch(question), aiExecutor)
            .orTimeout(1500, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> List.of());

    String intent = intentFuture.join();       // 到这里通常两个都已完成
    List<Document> docs = docsFuture.join();

    // 2) 只有真正需要生成时才调用 LLM，并给整条链路一个总预算
    return CompletableFuture
            .supplyAsync(() -> "shop".equals(intent) ? handleShop(question) : handleChat(question, docs, history), aiExecutor)
            .orTimeout(8, TimeUnit.SECONDS)
            .exceptionally(ex -> new ChatAnswer("小市有点忙，稍后再问我一次吧～", List.of()))
            .join();
}
```

再往前一步（最能体现"链路"）：**改成 SSE 流式**，接口立刻返回 200，token 边生成边推给前端。

```java
@PostMapping(value = "/ask-stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter askStream(@RequestBody Map<String, Object> body) {
    SseEmitter emitter = new SseEmitter(30_000L);
    aiExecutor.execute(() -> {
        try {
            emitter.send(SseEmitter.event().name("meta").data("start"));
            // ... 逐 token 推送
            emitter.complete();
        } catch (Exception e) { emitter.completeWithError(e); }
    });
    return emitter;   // Tomcat 线程立刻释放
}
```

- 体现的技术点：`CompletableFuture` 组合、`orTimeout`、降级兜底、`SseEmitter` 异步 Servlet、线程池隔离。
- 验收：`/api/chat/ask` P95 从 ~6.5s 降到 3s 内；SSE 接口首字延迟 < 1s；停掉 DeepSeek 后接口仍返回 200 + 兜底话术。

### 场景 B：下单主链路与旁路解耦 + 最终一致性 ★必做

**现状**：`OrdersController.create()` 一个方法写完所有事，且**没有事务**。

**改法 1：先补事务边界**（这是 bug，不是优化）

```java
@Service
public class OrderService {
    @Transactional(rollbackFor = Exception.class)
    public Orders placeOrder(Long consumerId, Long stallId, Long productId, int quantity, String remark) {
        // 校验 + 扣减/写订单 + 写明细，同一个事务
        ordersService.save(order);
        orderItemService.save(item);
        applicationEventPublisher.publishEvent(new OrderCreatedEvent(order));
        return order;
    }
}
```

**改法 2：副作用走事务提交后的事件**，慢操作不占主链路

```java
@Async("bizExecutor")
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)   // 关键：必须提交后
public void onOrderCreated(OrderCreatedEvent e) {
    pushToSeller(e.orderId());      // 推送摊主端
    updateDashboardCache();         // 刷看板缓存
    auditLog(e.orderId());          // 操作日志
}
```

**改法 3：失败不能丢，落 outbox 表 + 定时补偿**

```java
// 异步任务失败 → 写 async_task(status=0, retry=0)，由 @Scheduled 每 30s 捞出来重试，超过 5 次置为失败并告警
@Scheduled(fixedDelay = 30_000)
public void retryFailedTasks() {
    asyncTaskService.listRetryable(100).forEach(t -> {
        try { dispatcher.dispatch(t); t.markSuccess(); }
        catch (Exception ex) { t.markRetry(ex.getMessage()); }
    });
}
```

- 体现的技术点：`@Transactional` 边界、`TransactionPhase.AFTER_COMMIT`（异步线程读不到未提交数据这个坑）、事件驱动、幂等、失败重试、最终一致性。
- 验收：50 并发下单，订单表 = 明细表条数且金额一致；把通知逻辑改成抛异常，主事务不回滚、订单照常创建。

### 场景 C：看板并行聚合 + 缓存 ★性价比最高

**现状**：`AdminController.stats()` 4 次串行 + 全量 `reduce`。

```java
@GetMapping("/stats")
public Result<Map<String, Object>> stats() {
    CompletableFuture<Long> stalls    = CompletableFuture.supplyAsync(stallOwnerService::count, bizExecutor);
    CompletableFuture<Long> consumers = CompletableFuture.supplyAsync(consumerService::count, bizExecutor);
    CompletableFuture<Long> orders    = CompletableFuture.supplyAsync(ordersService::count, bizExecutor);
    CompletableFuture<BigDecimal> revenue = CompletableFuture.supplyAsync(statMapper::sumRevenue, bizExecutor);

    try {
        CompletableFuture.allOf(stalls, consumers, orders, revenue)
                .orTimeout(500, TimeUnit.MILLISECONDS)
                .join();
    } catch (Exception e) {
        log.warn("看板聚合超时，降级为缓存快照");
        return Result.success(cacheService.lastSnapshot());
    }
    // ...
}
```

同时把 `revenue` 改成 SQL 聚合（并行不能替代"别把全表捞进内存"），在 `OrdersMapper` 里加一个方法即可：

```java
@Select("SELECT COALESCE(SUM(total_amount), 0) FROM orders WHERE status = 3")
BigDecimal sumRevenue();
```

> 说明：上面的 `cacheService.lastSnapshot()` 是示意，降级兜底可以用 Caffeine/Redis 缓存上次结果，也可以直接返回 `0` 并打降级日志。

- 体现的技术点：`allOf` 聚合、统一超时、失败降级、缓存与并行的取舍。
- 验收：把 4 个查询人为各加 100ms 延迟，接口从 ~400ms 降到 ~110ms；把某个查询改成 sleep 2s，接口 500ms 内返回降级数据。

### 场景 D：定时批处理的分片并发 + 分布式锁（加分项）

新增"逾期账单催缴"：`@Scheduled` 每天扫描 `bill` 表 → 分页取 ID → 按 `stallId % N` 分片 → 固定线程池并发处理 → 汇总。

```java
@Scheduled(cron = "0 0 2 * * ?")
public void overdueJob() {
    if (!redisLock.tryLock("job:overdue", 10, TimeUnit.MINUTES)) return;   // 多实例只跑一个
    try {
        List<Long> ids = billService.listOverdueIds();
        List<List<Long>> shards = split(ids, 8);
        List<Future<Integer>> futures = batchExecutor.invokeAll(
                shards.stream().map(s -> (Callable<Integer>) () -> processShard(s)).toList());
        int total = futures.stream().mapToInt(this::get).sum();
        log.info("逾期催缴完成，共处理 {} 条", total);
    } finally {
        redisLock.unlock("job:overdue");
    }
}
```

- 体现的技术点：`invokeAll`、分片、线程池复用、Redis 分布式锁、优雅停机（`shutdown` 时等在途任务）。
- 验收：1000 条数据单线程 10s → 8 线程 1.5s；同时起两个实例只跑一遍。

## 3. 基础设施（四个场景共用，也是"专业度"所在）

### 3.1 线程池隔离 + 可视化

```java
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {

    @Bean("aiExecutor")    public ThreadPoolTaskExecutor aiExecutor()    { return build("ai-",    4,  8,  200); }
    @Bean("bizExecutor")   public ThreadPoolTaskExecutor bizExecutor()   { return build("biz-",   8, 16, 1000); }
    @Bean("batchExecutor") public ThreadPoolTaskExecutor batchExecutor() { return build("batch-", 4,  4,  200); }

    private ThreadPoolTaskExecutor build(String prefix, int core, int max, int queue) {
        ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(core);
        e.setMaxPoolSize(max);
        e.setQueueCapacity(queue);
        e.setThreadNamePrefix(prefix);
        e.setTaskDecorator(new MdcTaskDecorator());          // 传递 traceId
        e.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy()); // 反压，不丢任务
        e.setWaitForTasksToCompleteOnShutdown(true);         // 优雅停机
        e.setAwaitTerminationSeconds(30);
        e.initialize();
        return e;
    }

    @Override public Executor getAsyncExecutor() { return bizExecutor(); }

    @Override public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) -> log.error("[async] {} 执行失败", method.getName(), ex);  // 异步异常不会回到调用方
    }
}
```

**为什么必须分池**：AI 调用慢（3~8s），如果和业务共用一个池，一次大促的 AI 请求就能把下单接口的线程全占死——这叫"故障扩散"，面试必问。

### 3.2 traceId 贯穿

```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {
    @Override protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
        String traceId = Optional.ofNullable(req.getHeader("X-Trace-Id"))
                .orElse(UUID.randomUUID().toString().replace("-", "").substring(0, 16));
        MDC.put("traceId", traceId);
        res.setHeader("X-Trace-Id", traceId);
        try { chain.doFilter(req, res); } finally { MDC.clear(); }
    }
}
```

`logback-spring.xml` 里 `%X{traceId}` 打出来，配合 `TaskDecorator`，就能看到同一条链路在 `http-nio-exec-3` 和 `ai-2`、`biz-5` 三个线程里的日志。

### 3.3 优雅停机

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

### 3.4 指标（答辩现场可以投屏）

暴露线程池状态给 `/actuator/metrics` 或自己写个接口：

```java
@GetMapping("/api/admin/threadpool")
public Result<Map<String, Object>> pool() {
    return Result.success(Map.of(
        "ai.active",    aiExecutor.getActiveCount(),
        "ai.queue",     aiExecutor.getThreadPoolExecutor().getQueue().size(),
        "ai.completed", aiExecutor.getThreadPoolExecutor().getCompletedTaskCount()
    ));
}
```

## 4. 不建议做的事（能说出"为什么不"，比会用什么更加分）

| 不做 | 原因 |
|---|---|
| 全站上 WebFlux | MyBatis / JDBC 是阻塞驱动，混用只会更慢；改造面覆盖全部 Controller，收益不成正比 |
| 引入 MQ（Rabbit/Kafka） | 单机演示没有运维条件；用 outbox 表 + 定时重试就能讲清最终一致性，成本低一个数量级 |
| 无界队列线程池 | 队列无限 = 内存无限，OOM 只是时间问题；必须有界 + 拒绝策略 |
| 到处 `@Async` | 同类自调用不走代理会失效；且没有池隔离、没有异常处理，等于埋雷 |
| 只用 `CompletableFuture` 不加超时 | 外部依赖卡死时线程照样堆积，超时是异步的生命线 |

## 6. 面试 / 答辩必被问的 10 个坑（提前准备好答案）

1. `@Async` 为什么同类内部调用不生效？→ Spring 代理，必须跨 Bean 或 `AopContext.currentProxy()`。
2. `@Async` 方法上再加 `@Transactional` 会怎样？→ 是新事务，且提交时机在方法返回后；调用方事务未提交时异步线程读不到数据 → 用 `AFTER_COMMIT`。
3. 为什么不用默认的 `SimpleAsyncTaskExecutor`？→ 它不复用线程，每次 new，高并发直接 OOM。
4. 队列满了怎么办？→ `CallerRunsPolicy` 反压到调用线程（Tomcat），配合池隔离避免拖垮全局；也可以 `AbortPolicy` + 快速失败。
5. `MDC`/`SecurityContext` 为什么在异步线程里丢了？→ `ThreadLocal` 不跨线程，需要 `TaskDecorator` 手动搬。
6. `orTimeout` 真的能杀掉正在跑的线程吗？→ 不能，只是让 Future 提前完成；外部调用必须自己设 read timeout + 并发限流（`Semaphore`）。
7. 异步任务抛异常，调用方知道吗？→ 不知道，必须 `AsyncUncaughtExceptionHandler` + 落库。
8. 重试会不会重复扣款/重复发通知？→ 幂等键（业务唯一号）+ 去重表。
9. 优雅停机怎么保证不丢任务？→ `setWaitForTasksToCompleteOnShutdown` + `awaitTerminationSeconds` + `server.shutdown=graceful`。
10. 为什么 AI 用独立池？→ 慢调用隔离，防止一个外部依赖抖动把整个应用的线程池吃完。
